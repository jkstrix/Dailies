What is being built

The mod

  • Name: Dailies. Mod id: dailies.
  • Java package root: comedymonkey.dailies. Everything the owner publishes sits under comedymonkey.
  • Game: Minecraft Java 1.21.1 on NeoForge 21.1, Java 21.
  • Side: client only. It must load on a client that joins any server, modded or vanilla, and must never be required on a server.
  • Data folder: <game dir>/dailies/ for recordings, moments and exports.
  • Other people's voices: Dailies can record and log the voice chat of everyone the player hears. Agreeing that with the people being recorded is the user's responsibility; the mod gives them the means to leave anyone out (MOM-36) and says plainly where voice audio goes (MOM-37).
  • Not included: uploading to Medal.tv, a deliberate choice, and to any other service. Video goes out as files (chapter VI), ready for any service.

The pieces

  • Core (chapters II to VII, and XVI for other renderers): record, store, play back, edit, export. The code is in src/.
  • Smart Camera, Moments, MCP, the page (VIII to XI): the owner's features. Their source is in reference/ and plugs into the core through one interface. The Smart Camera is the owner's to change: anyone else may correct its ids, links and counts, and reports anything more instead of changing it.
  • Server companion (XII): the owner's separate server mod, provided complete.
  • What is provided (XV) and two appendices: every tool's arguments, and the stored records.
  • The Create and Aeronautics note, create-and-aeronautics.html beside this document: how contraptions and Sable craft were made to record and play back, fault by fault. It goes with chapter VII.

II

Recording

core

While a recording runs, Dailies keeps everything needed to show the session again exactly as the recorder's game received it, and adds the few things the game never receives about its own player.

Facts
  • A Minecraft client learns about the world only from what the server sends it: chunks, block changes, entities and their movement, particles, sounds, weather, time, chat and so on. This is true in singleplayer too, where the server runs inside the same program.
  • The server does not send a client its own player's movement, look direction, pose, arm swings or held item, because the client already knows them. A recording that is only "what was received" has no recorder in it.
  • Some of what arrives is about the connection, not the world: keep-alives, pings, resource pack prompts, login and configuration steps, chat signing data, the player's own open screens and inventory windows.
  • Mods send their own messages over the same connection ("custom payloads"), each with a namespaced id. NeoForge attaches extra spawn data to some modded entities in a payload of its own that arrives with the entity's spawn.
  • A connection can pass back through the configuration phase mid-session (some servers do this when moving a player between worlds). Registries may change when it does.

Deleting moves to the bin (REC-9), so it does not ask. Typing anywhere on the list starts a search; the arrows move the choice and Enter watches it.
REC-6If the game closes or crashes mid-recording, the next launch finds the unfinished recording and offers to recover or discard it. Recovery keeps everything up to the last data safely written.At most a few seconds may be lost.

It is a command of the game on the player's own computer, so it works on every server and never reaches one. What is captured

IdRequirementNotes
REC-10Everything the game receives about the world is kept, in order, with the tick it arrived on.World, blocks, entities, effects, sound, weather, time, scoreboard, boss bars, titles, chat.
REC-11Nothing about the connection or the recorder's private screens is kept: keep-alives, pings, login and resource pack steps, chat signing and session data, container windows, recipe books, advancement screens, statistics replies.The test is "would showing this again need the original server or leak the recorder's account?" One exception: what became of each server resource pack is kept, with the pack itself (REC-19), because without it the world is shown with the wrong textures, models and sounds. A second: the recorder's play screens are kept (REC-25, REC-29), as records of Dailies' own and never as the window packets themselves, which are still left out, as are the packets that open a book or a sign's editor.
REC-12The recorder's own player is captured so that it appears in playback like any other player: position, look and head direction, pose (sneaking, swimming, gliding, sleeping, riding), arm swings, held and worn items, item use, hurt and death, and the vehicle it rides.Update rate is an option, 1 to 20 per second; default 20.
REC-13Every recording also captures the recorder's hotbar, selected slot, health, hunger and experience, so playback can show their HUD. Always on; whether it is shown is chosen in the editor (the scene's "recorder's HUD" look, also in the Viewer card).
REC-14Other players' skins and names are captured as the recorder's game knew them, so playback needs no network.Playback must work offline.
REC-15Custom payloads from mods are kept as raw bytes with their id, without understanding them. A payload that cannot be kept is skipped and reported once per id in the log, never per message.See PLAY-12 for how they are shown again.
REC-16NeoForge's extra spawn data for an entity is kept with that entity's spawn and survives into every later snapshot that contains the entity.Without it, Create contraptions cannot be rebuilt.
REC-17Recording continues unbroken across dimension changes, respawns and a return to the configuration phase. A dimension change is, optionally, marked (default on).
REC-18If Simple Voice Chat is installed, an option captures the voice audio the recorder heard, per speaker, with positions, the kind of voice (another player or a fixed place; group chat; the recorder's own) and, for the first kind, the voice chat's range for it.Use that mod's public API only. Recordings without the kind treat a voice with a position as proximity and one without as group chat; without the range, 48 blocks. Also feeds Moments (MOM-30).
REC-19Every resource pack the server pushes, which the player accepts and the game loads, is recorded at the tick it comes into force with what the server said about it (id, address, hash, required or not, prompt), and the pack's bytes are stored inside the recording, once however often the pack is pushed. A pack the server takes off is recorded as removed at its tick. A pack the player declined, or that could not be fetched or loaded, is recorded as not applied. Packs applied before the recording started, as most are, are known from the moment of joining, and every snapshot says which packs are in force.The bytes are the game's own downloaded copy; nothing is ever fetched by Dailies. A pack is tens of megabytes against recordings of gigabytes, and the recording never depends on a cache or a server that may be gone (principle 2). Writing it must not stall the game.
REC-25The recorder's play screens are kept, in records of Dailies' own (dailies:windows): a window the server opened with a menu type (a chest, a furnace, a villager's trades, a mod's machine; a mod's window keeps the extra data NeoForge opened it with), a horse's inventory, and the player's own inventory, which the game opens with no word from the server. For each: which window and its title, every slot and the item on the pointer, its data slots (a furnace's flame and arrow), a villager's offers, and while it is open the pointer, in the window's own units, and the slot under it, a few times a second and at once when the slot under it or the item on it changes. Only what changed is written as play goes on; every snapshot holds the whole window. Recording works from an allow list, not a block list: settings and configuration, statistics, advancements, the recipe book panel, the pause menu and every other menu, the creative inventory (the owner's choice), and title, login, setup and debug screens are never kept. Books, the lectern and signs are play screens too, kept through Dailies' own compat (REC-29, REC-33 to 35) rather than here. In singleplayer a book pauses the game, and the recording keeps time while it is open, with the world standing still (REC-36). Within the allow list a short deny list, in code, leaves out server windows that are play screens but draw wrongly in playback (for now the stonecutter, whose recipe list comes from the recipes REC-11 leaves out); each is logged once.The exception to REC-11. The records are never handed to playback's packet handling, so the viewer's own inventory and windows are never touched (PLAY-20). Kept in the window's own units, the pointer lands on the same slot at any screen size or GUI scale.
REC-26The play screens and overlays of other mods are kept through their compats (CPT-1): a screen a compat claims by its class, a server window it claims by its menu type, extras for a server window Dailies records itself (what its screen holds that the server never sent: a tab, a selection, text being typed), and overlays drawn over play. At the end of each recorded tick each claim showing on the recorder's screen gives its state, the least that draws it again and always the whole of it, in bytes of the compat's own making. It is written under the compat's id, in records that carry the compat's version, when it first shows and then whenever it differs from the one written last, at most as often as the claim asks (text being typed, a few times a second); a claim that stops showing is written gone. Over a claimed screen the pointer is written as for the recorder's windows (REC-25), in the window's own units from the corner the compat gives, or as a share of the screen. A claimed screen class or menu type is the compat's alone: Dailies' own window recording leaves it out. The recording's manifest lists the compats that wrote into it, with their versions (compats).Records of a compat with no state of its own are never written, and nothing is recorded outside a recording. One claim per screen class or menu type: a second compat claiming it is left out with a line in the log. A claim whose state cannot be had is logged once and left out while it fails; the rest of the recording is unharmed.
REC-27Every snapshot holds the state of every compat claim showing at its tick, with the pointer. In playback a compat's records are played by keeping each claim's newest state, and what is held is described by writing those states again, so a jump into the middle of an open claimed screen shows it as it stood, a trimmed recording starts with it (FILE-10), and a combined one carries each source's records and lists the compats of every source, each at the newest version that wrote into any.Because each state is whole, a compat writes no snapshot code of its own. Proven by unit tests of the records (CompatHeldTest).
REC-28A compat stores what is large and seldom changes (a schematic's blocks) once in the recording rather than in a state written again in every snapshot: DailiesCompats.storeOnce takes the bytes, at most 16 MiB, and hands back a handle, the SHA-256 of the bytes as 64 hex digits, for the state to carry. The bytes go into the recording as shared data, packed as the rest is, once however often they are stored, and the manifest lists them (compatBlobs), written again at once the first time so a crash keeps them. Combining and trimming store every listed blob of each source in the new recording, once, and list it there (FILE-9, FILE-10). The recording holds the bytes themselves, never a path to where they came from, so it plays the same on any machine. Outside a recording nothing is stored and the handle is still given.Every blob of a source comes along, even when only a stretch that was cut named it: a compat's states are its own bytes, so which name a blob cannot be told. Proven by CompatBlobsTest: kept once, carried through a trim and a combine, found from a later snapshot.
REC-29The game's own books, lectern and signs are kept through a compat of Dailies' own, dailies:vanilla, which registers through the compat API (CPT-1) as the mods' compats do, the only one allowed in Dailies' namespace, so its states are written as REC-26 says, held in every snapshot and carried through jumps, trims and combines (REC-27). Each is a play screen, opened by using something in the world. Reading a written book from the hand (book_read, the game's book screen): which hand held it, found by its pages, or neither; the page open; and the book's pages, each as the game's JSON for its text, stored once in the recording (REC-28) and named by the state, never carried in it. The pointer is kept from the book's corner. Only the game's own screens of these kinds are kept: a mod's screen built on one of them is left out, as before.The pages are stored once because a book holds up to a hundred of them; a book held open is encoded again only when its pages change. A page turned shows at the tick it was turned, in singleplayer too, where the book pauses the game and the recording keeps time while it is open (REC-36).
REC-33A book on a lectern (lectern) is claimed by its window's type, minecraft:lectern, so Dailies' own window recording (REC-25) leaves it out: its window is the server's, but its screen is a book's, which keeps its pages and page to itself, is laid out as a book rather than a window, and has a Take Book button only for a reader who may build. Kept: the book's pages, stored once (REC-28), the page open, which follows each page turned, and whether the reader could take the book.Drawn by stage 1's window path, the screen would have taken its buttons from the viewer rather than the recorder and kept its pointer as a share of the screen.
REC-34Writing in a book and quill (book_write, the game's book editing screen, with its signing step): the page open and its text as typed, the cursor and the selection on it, whether the signing screen shows, the title as typed there, and the writer's name it shows under the title. The other pages are stored once (REC-28), with the open page left empty among them, so they change only when a page is turned or added and a write carries only the page typed on. Written at most five times a second while it changes.The book's pages are what the screen holds, not the item: the live screen sends them to the server only when Done or Sign and Close is pressed.
REC-35Editing a sign (sign_edit) or a hanging sign (hanging_sign_edit), each the game's own editing screen: which sign, by its place, its block (which gives its wood and whether it stands, hangs on a wall or hangs from above), its wood's name and whether it hangs; the side being edited; the four lines as typed; the line typed on with its cursor and selection; and the text's colour and glow. Written at most five times a second while it changes. The pointer is kept from the sign's middle.The lines as typed, not the sign's: the playback world's sign gets its text from the server's update when editing ends, as it did in play.
REC-36In singleplayer the game pauses under a book read or written, as under the pause menu, and stays paused: its world stops ticking. While it stands paused under a play screen the recording keeps (one a compat records whole, Dailies' own books and signs among them, or a window REC-25 keeps), the recording keeps time: a tick is recorded for every tick of the game's clock, twenty a second, with the screen's state as REC-25 to 29 and 33 to 35 say (pages turned, words typed, the pointer) and nothing of the world, which has not moved, the recorder's own body included. Each such tick carries a record of Dailies' own (dailies:still), written ahead of the tick's count, saying the world stood still. The recording's tick count, the time recorded on screen (REC-4), its time index (FILE-16), with the game time standing and the real time going on, and its snapshots, one each REC-20 interval as ever, all go on through it. In playback and exports the world is not ticked for those ticks, so nothing in it moves and the time of day stands, and it is drawn where it stood, as the live game drew it, while the screen, its pointer and the camera go on with the recording's time; the game's sounds already playing go on and no new ones start, as live, and voice chat recorded meanwhile is heard in step. Under any other screen that pauses the game, the pause menu above all, nothing is recorded and the recording's clock stops with the game's, as before. On a server, or in a world opened to LAN, nothing pauses, so nothing changes.The owner's choice (19 November): the game's pause is kept, and the book in the recording with it. A screen counts only while its claim gives a state for it, so a mod's screen built on a book, which the book's claim turns down, stops the clock as before. Proven by unit tests of the rule and of where playback stands still (StillTicksTest), and in game by the books' display test (TEST-8), which reads and writes its books in singleplayer.

Compats

How another mod's screens and overlays get into recordings: a small API that a compat implements. The owner's own mods (Post Rider, ComedyMonkey's Create Addons, McpCraft) implement it in the mods themselves; a compat for another person's mod is a subproject of this repository, started from the template (CPT-5).

IdRequirementNotes
CPT-1The compat API, in comedymonkey.dailies.api.compat. A compat implements DailiesCompat (a namespaced id outside Dailies' and Minecraft's namespaces, which only Dailies' own compat for the game's books and signs uses (REC-29), a version of 1 or more, its claims, and an optional display test) and is registered with DailiesCompats.register while its mod loads. Doing no harm

Never stall the gameCompression and disk writes happen off the game thread. Recording must cost no visible frame time in normal play.
Never crash the gameA failure anywhere in recording ends the recording, tells the player, and leaves the game running.
Bounded memoryIf the disk cannot keep up, the queue has a limit; reaching it pauses capture and says so, it does not eat memory.
Never change what the player seesRecording is invisible to gameplay, to other mods and to the server.
III

The recording file

core

Dailies has its own format. The layout below is original to this document and is only a suggestion; what the format must be able to do is binding.

IdRequirementNotes
FILE-1One recording is one file with the extension .dailies, which a person can copy, rename and delete.Recordings live in dailies/recordings/, sub-folders allowed.
FILE-2The header can be read without reading the rest: a unique id for the recording, format version, name, when it was made, game and data version, total ticks, the recorder's name and id, the world or server name, the list of segments with their start ticks, the markers, and every mod present with its version.Lists and menus need this to be instant.
FILE-3Renaming or moving the file must not break anything that refers to it. Everything refers to the recording by its unique id.Moments and editor state both do.
FILE-4Segments are independently readable and compressed. A damaged segment makes that stretch unplayable and no more; a damaged chunk listing (FILE-5) costs the jumps to the snapshots up to the next whole listing their chunks, never playing through them. Every block is compressed by itself with Zstandard and dictionaries the file carries: one for shared data, one for segment parts, each stored once at the start of the file. A recording opens with the dictionaries it was written with, never the mod's current ones, so a later version with dictionaries trained afresh still opens it.Level 9, with two dictionaries of 64 KB trained on real recordings (gradlew trainDictionaries), the one for shared data on chunks cut by section as FILE-5 stores them. Against deflate level 3 that is some 86% of the size, unpacked more than twice as fast. Trim and combine write the mod's current dictionaries, copying blocks from a source with the same ones as they are and packing again what comes from one with others. A block says how long it is unpacked, and more than 64 MB is damage, never memory to find.
FILE-5Identical chunk data repeated across snapshots is stored once, and a chunk is stored by section, so a change to one block stores that section again, not the whole chunk. A chunk, as it arrived or as a snapshot describes it, is a small piece list kept as shared data and named by its SHA-256; the packet is its pieces end to end. A piece is bytes written out in the list, the name of a part (other shared data, named by its own SHA-256), or the name of an inner list, which holds only bytes and parts. A chunk's parts are its heightmaps, its block entities, each 16×16×16 section's block states and biomes as the section writes them for the network, and each section's sky light and block light, separately; its sections are gathered in one inner list and its light in another. The light a snapshot gives a chunk whose blocks are as stored is kept the same way. Playback puts each packet back together byte for byte and applies it as before; trim and combine carry every part and list a chunk names with it.
A snapshot names its chunks in a listing kept in a block of its own, not in its records, which only say where the chunks go: for each chunk its position, the name of its piece list, and the name of any light put on top. Every tenth snapshot's listing is whole; each snapshot between stores only the changes from the one before: chunks whose names changed (the name alone of new light on an unchanged chunk), chunks added, chunks gone. A jump puts its snapshot's listing together from the last whole one and at most nine sets of changes, and the recording keeps the listings it puts together, so dragging the playhead back and forth over the same stretch builds nothing twice. Trim and combine write every listing afresh from its source: whole at the first snapshot of a piece, and otherwise the changes from the snapshot before it in the new recording.		Most chunks do not change between snapshots; without this, long recordings are enormous. Within one that does, most of it is as it was: a door, a crop, a furnace or a light that changes stores a section, its light and two small lists again, not a column of some 36 KB. Every all-dark and every all-lit section of light in a recording is one part, and every section of air another. Parts are stored before the lists that name them and lists before the records that do, so a crash never leaves a name whose data is missing. A packet laid out other than expected (a mod's doing) is cut into fewer pieces, never stored wrong.
Names are random, so nothing packs them smaller, and a snapshot every two seconds named some six hundred chunks, nearly all named by the snapshot before too. Measured on the generated-terrain tour (7.8 minutes, 239 snapshots), the names came to 6.7 MB packed and the listings come to 1.5 MB. A listing block comes before the part whose records say where its chunks go, so a crash never leaves a snapshot naming a listing that is not there. The parts of an entity a snapshot describes again each time (its data, attributes and equipment) stay in the records: measured on the same tour, storing them once by their SHA-256 cost more than it saved at every size it was tried from, being shorter than a name on average (12 to 27 bytes) and packing well beside each other.
FILE-6A small preview image can be stored and shown in the list.
FILE-7The format version is checked on open. A newer file than the mod understands is refused with a clear message. Older versions keep opening for as long as is practical.Version 2 is the first packed with Zstandard (FILE-4); version 3 the first whose snapshots name their chunks in listings (FILE-5). Before release nothing older is kept: a recording of version 1 or 2 is refused with a message.
FILE-8Editor state (chapter V) is stored beside the recorded data in the same file, and can be rewritten without rewriting the recorded data.Editing a two-hour recording must not copy gigabytes on every save.
FILE-16The time index. Every recording stores, for every tick, the real time and the world's game time, readable without playing the recording.A few bytes a tick. It can never be added to a recording afterwards, so it is recorded from the first version. FILE-14 falls back on it, and recordings of the same session from several points of view line up by it.
FILE-15Sharing a session. "Share session" packs a recording and the moments sessions it was made in into one file, .dailiesshare, to send to a friend: a zip holding share.json (format, the recording's id and name, who recorded it, when it was packed), recording.dailies as it is, and moments/<session id>/ for each session. "Import" takes a friend's pack in: the recording into the recordings folder under shared/<their name>/ (left out when a recording with its id is there already), and their moments sessions onto the moments page, each under an id of its own and marked as theirs (imported, shared_by). In the recordings list, Share packs the chosen recording; Import takes every pack in the Dailies import folder, and opens that folder when it is empty.Other players are treated fairly: a pack holds only the sharer's own voice lines and audio; what others said stays on the sharer's computer. Names in a pack that would land outside its folder are refused. A pack from a newer format is refused with a message. Tools: replay_share, replay_import.

IdRequirementNotes
FILE-9Combine. Recordings can be joined, in any order, into a new recording; the sources are left untouched. Each source keeps its own world: at a join the world is rebuilt from the next source's opening snapshot, so recordings from different worlds or dimensions combine cleanly. A join is marked on the timeline and adds no ticks. Sources made with different game versions are refused; different mods are allowed and listed (PLAY-5, per source).Over MCP: replay_combine. FILE-10Trim. Ranges can be kept or cut out of a recording into a new one, such as the hour spent mining; the source is left untouched. A range that starts where a segment starts is copied as it is. FILE-11The source map. A recording made by combining or trimming stores in its header the stretches of original recordings it is made of: for each, the original's id, its range of ticks and where it starts here. Spans always point at originals: editing an edited recording carries its spans across, adjusted, so every map is one step deep however many edits there were. A plain recording has no spans and stands for itself.A moment recorded at tick 50,000 of A, in a recording whose second span holds A's ticks 48,000 to 72,000 from tick 36,000, is at tick 38,000 there.
FILE-12The index. dailies/recordings/index.json lists every recording's id, file, size, modified time and spans. FILE-13Choosing the file to open. When a moment or clip is cued: if the open recording holds it, jump there; otherwise open the original, if it still exists; otherwise the newest recording that holds it. A clip with a cut inside plays as the edit has it, its pieces back to back, and is flagged cut with the length removed.Moments are never rewritten: they keep the id and tick of the recording they were made in. FILE-14Asking where a moment is. The core answers, through Host (chapter XV), every recording that holds a moment or a clip, best first in the order of FILE-13, with its tick or stretches there, and whether the open recording holds it. IV

Playback

core

Opening a recording puts the viewer inside the recorded session as a free camera. Nothing is simulated: everything that moves does so because the recording says it did.

Facts
  • The simplest way to show recorded data again is to give the real client a real connection to something that speaks the server's side of the protocol and sends the recorded data at the recorded times. The client then draws it with all its normal code, mods included.
  • A client connected this way expects a player of its own. That player can be the viewer: invisible, in spectator-like flight, and never sent anywhere by the recording.
  • NeoForge fires its server lifecycle and tick events for any integrated server. Other mods react to those and may try to run their gameplay logic on a playback world.
  • Entity movement arrives at most once a tick. Smooth motion between ticks is the client's own interpolation.

PLAY-2The viewer is a camera the person flies freely, through blocks, at an adjustable speed. It is not part of the recording and nothing in the recording can move, hurt or teleport it.Flight options: momentum, axis locks, horizontal or look-relative movement.

Create and flying machines

core

The video series this mod exists for is about Create contraptions and Create Aeronautics aircraft. They must record and play back correctly, including people riding them. This is the hardest part of the core, so the facts are spelled out. How each fault was met and put right, with the names it relies on in the other mods, is in the technical note Create and Aeronautics.

No hard dependencyDailies loads and works without Create, Sable or Aeronautics. All support for them switches on only when they are present.
No copied codeReach these mods through their public APIs, or by reflection on their public classes. Never bundle their code.
Tested versionsCreate 6.0.10, Sable 2.0.6, Create Aeronautics 1.3.2 for Minecraft 1.21.1.
Facts: Create contraptions
  • A contraption (the thing a mechanical bearing, piston or cart carries) is an entity. Its blocks travel in NeoForge's extra spawn data (REC-16), not in the world.
  • Rebuilding that spawn data from an entity on a playback world fails, because the entity there is an empty shell. The recorded spawn data must be sent again as it was recorded.
  • Contraption movement and assembly state arrive as ordinary entity data and as Create's custom payloads.
Facts: Sable physics objects (Create Aeronautics)
  • Sable keeps the blocks of each physics object (a "sub-level") in a hidden region of the same world, tens of millions of blocks from where it appears. The client draws those blocks moved and rotated into place.
  • Sable creates, resizes and removes sub-levels with its own custom payloads over the normal connection. Chunk data for the hidden region arrives as ordinary chunk packets.
  • The object's position and rotation are sent many times a second over a separate UDP channel that Sable opens beside the normal connection. It does this even in singleplayer. A recording that only watches the normal connection gets objects that never move.
  • Sable's client smooths motion using recent poses and ignores a pose it considers too old. After a jump in playback, the first poses must still be accepted.
  • Entities that belong to an object (seats, glue, rotor contraptions) have positions inside the hidden region. Sable marks packets for such entities so its client keeps them there; an unmarked position inside the region is read as "standing on the object" and moved out into the visible world.
  • A player standing loose on a moving object is carried by Sable's client-side logic, not by position packets alone.
  • Some of Sable's payloads act on the recorder's own connection or body (opening the UDP channel, freezing the player, entering an editing mode). Playing them back is harmful.

How the director decides

  1. Read the situation

    What the subject is doing (still, walking, running above 5 blocks a second, swimming, flying, riding; a change has to last half a second), how enclosed the space is (rays out to the sides and up), and moments of action: a turn of more than 60° within a second, taking off, landing, getting on or off something, going into or out of a tight space.

  2. Decide whether to cut

    Never before 1.8 s (36 ticks, counted in ticks, so that no shot is under 1.5 s on the exported frames). After that, cut at once when the view has been more than half blocked, or the camera squeezed within 1.2 blocks of the subject, for 0.3 s, or a tripod's subject has left it for good. After the minimum length, cut on a moment of action (within a second of it; into or out of a tight space it is an establishing shot), when the activity has changed, or when the shot reaches its planned length: the maximum at walking pace, nearer the minimum as speed rises to 10 blocks a second (flying and riding count as fast), varied by ±15%.

  3. Pick the kind of shot

    By weighted chance (chase, over the shoulder, side tracking, tripod, orbit). Enclosed: 3, 2.5, 0, 1.5, 0. Flying: 3, 0.3, 2, 2, 0.5. Riding: 3, 0.8, 3, 2, 1. Running: 3, 1.5, 2.5, 2, 0.5. Still: 1, 2, 0.5, 2, 3. Otherwise: 2.5, 2, 1.5, 2, 1. Kinds switched off get 0; the kind just used has its weight quartered.

  4. Check before cutting

    Each candidate is set up and checked: the camera has room, it sees at least three quarters of the subject, it looks from at least 35° away from the shot before both in the way it looks and in the way it sees the subject (no jump cuts), and it is on the same side of the line of action (the way the subject travels, or faces when still; within a quarter of a block counts as on the line) as the camera is now. Up to eight candidates are tried; when none passes, the shot carries on and the director tries again a quarter of a second later. A blocked shot that must go takes the candidate with the clearest view that still turns 32° and keeps to the side of the line. The angle is checked against the camera of this tick and of the tick before. After a jump of the subject the first shot is still no jump cut from the camera before.

  5. The shots

    Establishing: a slow (6° a second), high (6 blocks) and wide (16 blocks) orbit, or in a tight space a tripod 11 to 14 blocks off. Chase: distance ×0.9 to 1.3, height ×0.7 to 1.3, up to 25° off behind. Over the shoulder: 2.2 blocks behind and 0.45 above, 15 to 25° to one side, the subject at 0.3 of the frame on that side. Side tracking: 75 to 100° to the side, distance ×1 to 1.4. Tripod: placed by itself, on the kept side of the line. Orbit: radius ×0.8 to 1.3, 10 to 18° a second either way, starting 50 to 140° round from the camera before. Each shot's camera is the solver of that mode, as smooth as it is on its own.

  6. Stay repeatable

    All chance comes from the keyframe's seed and the tick a cut falls on; the camera is worked out per tick (CAM-7). Playing the same stretch again gives the same edit. Cuts are instant. A jump, a teleport or a settings change starts the edit again.

Building clips

  1. Choose the triggers

    Every event that scores at least the minimum (default 25), after the ignore list and any filters (player, type, time range, keyword).

  2. Give each a window

    From momentsClipPreRollSeconds (15) before to momentsClipPostRollSeconds (20) after.

  3. Cluster

    Events whose windows overlap become one clip.

  4. Keep sentences whole

    Widen a clip by up to 30 s on each side so no voice segment is cut. Merge clips that grow into each other.

  5. Add conversations

    A stretch with at least 25 words within 20 s from at least two speakers is a clip even with no event. Segments less than 10 s apart are one conversation. This step needs transcripts, so it only finds anything with AI on.

  6. Score, rank, cap

    An event clip scores its best event plus 3 per extra event (up to +20). A conversation scores 25, plus half a point per word (up to +45), plus 5 per speaker beyond the first. Keep the best 20 by default.

  7. Describe

    Each clip stores: title, summary, start and end time, duration, recording id with start and end tick, its events, players, full transcript and score. The MCP server

yours

Dailies contains a Model Context Protocol server, so an AI agent can do everything a person can: record, open, seek, edit, export, and query moments. It listens only on the player's own machine unless the player opens it to others, and then only behind HTTPS, a token and a list of allowed machines, while the player's own machine goes on as before.

IdRequirementNotes
MCP-1Transport is MCP Streamable HTTP at POST /mcp, JSON-RPC 2.0, single messages and batches. Every request is answered in full with a Content-Length; there is no event stream. GET /mcp answers 405.Methods: initialize, ping, tools/list, tools/call; notifications answer 202.
MCP-2It binds to 127.0.0.1 only, unless MCP-8 is switched on, on mcpPort (default 25595), and can be switched off with mcpEnabled. Changing any of its settings restarts it without restarting the game. A port already in use is reported in the log and is not fatal.Another mod's MCP server in the same game must be able to run beside it on its own port.
MCP-3A request with an Origin that is not localhost is refused (403), and so is one whose Host is not localhost. Headers are limited to 16 KB and bodies to 1 MB. Chunked bodies are refused.Stops web pages and DNS rebinding from driving the game.
MCP-4Tools that touch the game run on the client thread and the HTTP thread waits for them, with a timeout. Tools that only read files run on the HTTP thread. Editing tools go through the editor's undo stack.No dependency on an MCP library: a plain socket and the JSON library the game already ships.
MCP-5A tool's result is one JSON object as text. A tool failure is a normal result with isError and a message that says what to do next. Unknown argument names are rejected with the list of valid ones; out-of-range numbers are rejected with the nearest allowed value.
MCP-6Tools that start slow work (opening a recording, exporting, jumping) return at once and say how to poll for the result.
MCP-8Reaching it from another machine is off until mcpBind (default 127.0.0.1) is set to one of the computer's own addresses, or 0.0.0.0 for all of them. Then the one port answers two kinds of connection, told apart by the first byte each sends (a TLS greeting starts with 0x16; no HTTP request does):
· plain HTTP is this computer's own agents and page, exactly as before: no token, localhost names only (MCP-3). It is answered only when the connection comes from 127.0.0.1 or ::1; from anywhere else it gets a short plain-text 400 saying to use HTTPS. Bound to a single network address, the server also keeps listening at 127.0.0.1 for these;
· HTTPS is everyone else, and is held to all of the following whatever address it comes from;
· the certificate is made on first use and kept in dailies/mcp/certificate.p12. Its SHA-256 fingerprint is written to the log and to the setting mcpCertificateFingerprint, so a client can pin it;
· the client's address must be in mcpAllowedClients (addresses or CIDR ranges; default the private local-network ranges; this computer is always allowed). Others are dropped before anything is read;
· every HTTPS request but GET / must carry Authorization: Bearer <mcpToken>, else 401. The token is made the first time remote access is switched on;
· five wrong tokens from one address within a minute shut it out of HTTPS for a minute (429 with Retry-After), whatever it sends meanwhile;
· the Origin and Host checks of MCP-3 apply to HTTPS widened to the bound address (for 0.0.0.0, to the computer's own addresses and name).		For anyone who leaves mcpBind alone, nothing changes: plain HTTP on 127.0.0.1, no token. With remote access on, local agents and a remote one work at the same time. The page is served over HTTPS without the token because a browser cannot send one when opening a page; it holds no data and asks for the token itself (chapter XI). The certificate names the bound address; binding to an address it does not name makes a new one.
MCP-7moments_cue takes a clip id or an event id. If the right recording is open it jumps there (for an event, lead_seconds earlier, default 5) and pauses. If not, it opens that recording and jumps once it has loaded. It refuses to leave a live world unless leave_world is true. With camera true it also adds the clip's suggested Smart Camera at the cue point, following the recorder.The refusal message starts with LEAVE_WORLD_NEEDED so the page can ask the person.

The moments page

yours

The same local server answers GET / with a web page for browsing a session's moments and cueing them up. It is one self-contained file that talks to /mcp from the same origin, and it is provided: reference/src/main/resources/assets/dailies/web/moments.html.

What it shows

  • A session picker, a refresh button, and whether tracking and AI are on.
  • A strip of the whole session: clips as bands, events as bars whose height is their score. Clicking one scrolls to it.
  • Clips: best first, with title, summary, time, length, players, the events inside, what was said, and the suggested camera with its reason.
  • Events: each with time, type, a "first" badge, where it came from, position and tick; filters for type, minimum score, text and firsts only; sort by time or score; the full record on request.
  • Voice: the lines in order, or a note that they are not transcribed.
  • Ignored: the ignore list, with add and remove.
  • Privacy: the players whose voice is left out (MOM-36), with add and remove and the speakers of this session one click away; and where voice audio goes (MOM-37), which is also said in a notice at the top of every tab.
  • Pictures: an event that has a picture (MOM-40) shows it, and a clip shows the picture of its best event that has one. Clicking enlarges it.
  • The live lamp: green while the live feed is open, brass while the page is refreshing by the clock, grey when paused.

What it does

  • Find clips with a minimum score and a maximum count.
  • Cue + camera and Cue only on a clip; Cue on an event (five seconds early).
  • PAGE-4. Make scene on a clip: calls moments_clip_to_scene. When the recording that holds the clip is not the one open, the page cues the clip first (asking before leaving a live world, as a cue does), waits for the recording to load, and then makes the scene. The scene is named after the clip, exports exactly the clip and has the suggested camera; one undo in the editor takes it away.
  • PAGE-5. Export on a clip, and tick boxes with Export selected: each clip gets a scene as PAGE-4 makes it, and an export of that scene on the export queue (EXP-10), one job per clip, through moments_clip_to_scene with export, which calls Host.queueExport. The preset is chosen once above the clips. Files are named from the clip's title and the day it happened. Clips in other recordings are opened one after another; leaving a live world is asked once. Start queue starts the queue in the background (EXP-13).
  • Asks before pulling the player out of a live world.
  • Ignore kind on an event adds its type (or, for a custom event, its name) to the ignore list.
  • PAGE-1. Live: the page keeps GET /live open, a server-sent event stream of its own that is not part of MCP. Each message names what changed (event, dialogue, interaction or clips, with the session, the record's id and added or changed); the page then reads it through the usual tools, so new events, clips, transcripts and pictures appear the moment they happen.
  • PAGE-2. Fallback: if the stream cannot be opened or drops, the page refreshes every ten seconds while the session is running and keeps trying to reconnect by itself. Neither way redraws under an open details box or a half-typed entry.
  • PAGE-3. Token: when the game answers 401, which it only does over HTTPS (MCP-8), the page asks for the token once, keeps it in that browser, and sends it with every request, the stream and the pictures included. It can be forgotten from the Privacy tab.

Rules

  • No external scripts, fonts or requests: it must work offline.
  • Everything shown comes from other players' names and chat, so it is inserted as text, never as markup. This page can drive the game.
  • Light and dark by the browser's preference, in the house colours of this document; usable from a phone-width window to a wide monitor.
  • The server carries at most eight live streams, drops one that stops reading, and sends a comment line every 15 s so a closed page is noticed.
  • Pictures are served from GET /pictures/<session id>/<event id>.jpg, from the session's own pictures folder and nowhere else.

  1. Record

  2. Build machines

    Place a bearing contraption driven by a motor, a Sable platform, a helicopter with a seat (sit in it before assembling), and a hot air balloon with a lit burner (stand in it before assembling). Note the live position of each at several ticks. MOD-1 to 4, REC-22.

  3. Play back

    Open the recording. At each noted tick, reached once by playing and once by jumping, each machine is within a third of a block of its live position, the seated player is on the seat and the standing player is on the deck. Jump backwards twice; nothing is duplicated. The balloon is followed through its climb and descent, with everyone in its basket and its burner lit and out when it was, and Host.crafts() knows each craft by an id that stays the same across jumps. PLAY-11, MOD-2 to 5.

  4. Server resource packs

    The world's built-in server pushes a small pack, made by the test and served from the same machine, and the script accepts the game's question; then, while recording, the server takes it off, pushes one that is declined, and pushes the first again. The recording holds the pack's bytes once. Playback has the pack in force on opening and not after closing, off at a tick before the second push and on after it, off with the scene's look setting off, and never has the declined pack; a jump between two ticks with the same packs reloads nothing; stills exported with and without the pack differ; the viewer's own pack list is unchanged afterwards. The packs are then pushed and taken off many times over, quickly, while another thread measures text throughout, as other mods do: after every reload the game draws text with the font that reload made, never one it closed. REC-19, PLAY-17.

  5. Combining and trimming

    Every tick of the scripted recording has its real time and game time, read without playing it. Trim it around the kill and cue the kill: the trimmed recording opens at the right tick. Cue a moment in the stretch that was cut: it says so and names the original. Cut through the middle of a clip: it plays as two pieces and is flagged with the length removed. Combine the trimmed recording with a second one from another world: earlier clips still cue correctly, the join switches worlds without adding ticks, and clips from the second recording land after it. Delete the original and cue again: the edited recording answers. Delete the index, and separately rename a recording outside the game: the index repairs itself and every cue still works. Take a moment's recording id away by hand: it is still found by its time. Scenes, markers and server resource packs come through the trim and the combine, and a cut inside a segment with machines in the world gives a snapshot that plays them where they were. FILE-9 to 14, FILE-16.

    Add camera keyframes, undo and redo them, export ten seconds at 1080p with sound, and check the file's length, frame count and that its frames are not blank or scrambled. Export a still. EDIT-3, 6; EXP-1, 2, 7.

  7. Codecs, presets and separate sound

    The codec list offers only what this machine encodes, fastest first and the first the default, each saying hardware or software and on what; nothing is OpenH264, x264 or x265, H.264 is either offered on hardware or said to be missing and why, and asking for a codec it cannot use is refused with no file left behind. Other renderers

core

Create draws its moving parts through Flywheel, Create Aeronautics draws some of its effects with Veil, shader packs replace the game's drawing through Iris (or Oculus), Sodium (or Embeddium) replaces how terrain is built, and Distant Horizons draws terrain far beyond the view distance. Each changes how a frame comes to be. Playback and export must be as right with them as without them. Numbered XVI, after the others, so that no chapter number already referred to elsewhere changes.

No hard dependencyDailies loads and works without any of these mods. What is done for each switches on only when it is present.
Public parts firstReach each through its published API where it has one, else through its own settings or by name, and fail soft: one line in the log when a version is not the one Dailies knows, and everything else goes on working.
Tested versionsFlywheel 1.0.6 (inside Create 6.0.10), Veil 4.3.2 (inside Sable 2.0.6), Iris 1.8.14, Sodium 0.8.13 and Distant Horizons 3.3.3, for Minecraft 1.21.1. On NeoForge 1.21.1 Iris and Sodium are the mods; Oculus and Embeddium are their names on older versions and are treated the same.
Facts: how these renderers keep time
  • Flywheel moves each thing it draws once per frame, to the frame's point between two ticks, and finishes a tick's work before starting the next, so several ticks run in one frame are each done in full. To save time in live play it can also move far-off things only on some frames: its "limitUpdates" setting, on by default, updates something more than about 45 blocks away on every second frame, every third beyond 64, and so on. Flywheel reads the setting when it starts on a world.
  • Iris gives shader packs a frame counter, which goes up by one for every frame drawn, and a frame timer (frameTimeCounter, frameTime) read from the real clock at the start of every frame, in whole milliseconds. Packs animate water, wind and clouds by the timer, and build up their picture over frames (temporal anti-aliasing, exposure) by the counter. The game's own time of day and the frame's point between ticks reach Iris the usual way.
  • Veil sets a VeilRenderTime uniform from the real clock each time a shader's usual uniforms are set.
  • Sodium replaces the game's terrain building, and answers the game's own questions of whether every section is drawn and how many are, which is what an export waits on (EXP-5).
  • Distant Horizons keeps a store of far terrain per world or server, builds it from chunks the game loads, and draws it over many frames after a world opens. It offers an override for the folder each world's store is kept in, a way to hand it a chunk, and a way to read what its store holds.
